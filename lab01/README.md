### 1. Общая идея. 
**Предметная область:** Система управления меню для ресторана быстрого питания (аналог «Ростикс»).

**Проблема:** В нашем ресторане есть куча разных позиций: бургеры, картошка, напитки, крылышки. Каждая позиция (`MenuItem`) состоит из множества ингредиентов (булочки, котлеты, соусы, сиропы) и дополнительных опций (добавить бекон, сыр, лед). 

Если создавать объекты товаров через обычный конструктор (как показано в реализации без паттерна), мы сталкиваемся с классической проблемой «телескопического конструктора» (или конструктора-монстра). В моем коде без паттерна конструктор принимает **31 параметр** (из них 26 — это `bool` флаги наличия того или иного ингредиента)! 

**Почему это плохо?**
Во-первых, при добавлении в меню нового ингредиента (например, соуса барбекю), мне придется менять конструктор и переписывать создание **вообще всех** товаров в меню. Во-вторых, вызов такого конструктора выглядит как `new MenuItem("Чизбургер", 99, ..., true, false, false, true...)`. В этой бесконечной веренице `true` и `false` очень легко ошибиться и случайно налить сироп от колы в картошку фри, а лед положить в бургер. Чтобы не сойти с ума при расширении меню, нужен другой подход.

**Цель:** Разработать систему пошагового конструирования позиций меню с помощью паттерна «Строитель», чтобы сделать код масштабируемым, а создание объектов — читаемым.

### 2. Решение: как используется паттерн в вашем проекте.
Я внедрил(а) порождающий паттерн **Builder (Строитель)**. Теперь вместо того, чтобы передавать огромный список аргументов при создании объекта, я собираю товар пошагово, вызывая только те методы, которые нужны конкретному бургеру или напитку.

**Как это работает в коде:**
*   **Продукт (`MenuItem`):** Конечный объект, который мы строим. У него есть списки `DefaultIngredients` (базовый состав) и `AvailableExtras` (допы за отдельную плату). Теперь у него нет гигантского конструктора.
*   **Строитель (`MenuItemBuilder`):** Класс, который инкапсулирует логику сборки. Он содержит методы для добавления каждого конкретного ингредиента (например, `AddBuns()`, `AddBeefPatty()`, `AddExtraCheese()`). Каждый метод возвращает ссылку на самого строителя (`return this;`), что позволяет выстраивать цепочку вызовов (fluent interface). В конце вызывается метод `Build()`, который возвращает готовый `MenuItem`.
*   **Директор (`MenuManager`):** В моем случае роль директора (управляющего процессом сборки) берет на себя метод `LoadMenu()`. Он знает рецепты и вызывает методы строителя в нужной последовательности для создания каталога («Чизбургер», «Шефбургер», «Кола» и т.д.).

### 3. Диаграмма классов для архитектуры приложения с применением паттерна

*(Примечание для тебя: саму картинку тебе нужно будет нарисовать в draw.io, StarUML или PlantUML. Ниже я даю точное описание, что там должно быть нарисовано, и код для генератора).*

**Описание диаграммы для отрисовки:**
1.  **Класс `Ingredient`**: Поля `Name` (string), `Price` (int). Конструктор `Ingredient(name, price)`.
2.  **Класс `MenuItem`**: Поля `Name`, `BasePrice`, `Category`, `ImageUrl`. Списки `DefaultIngredients` и `AvailableExtras` (связь агрегации с классом `Ingredient`).
3.  **Класс `MenuItemBuilder`**: Имеет приватное поле `_item` типа `MenuItem`. Содержит методы `Create(...)`, `SetImage(...)`, множество методов типа `Add...()` (например, `AddBuns()`, `AddBeefPatty()`) и метод `Build()`, возвращающий `MenuItem`.
4.  **Класс `MenuManager`**: Содержит список `Catalog` типа `MenuItem`. Имеет метод `LoadMenu()`. Связан со строителем зависимостью (использует `MenuItemBuilder` для создания объектов).

*(Дополнительных диаграмм вроде диаграммы состояний для Строителя рисовать не нужно, так как этот паттерн порождающий, а не поведенческий. Диаграммы классов здесь вполне достаточно).*

### 4. Вывод: как внедрение паттерна повлияло на работу программы.

В реализации **без паттерна** код выглядит как настоящий ночной кошмар первокурсника. Чтобы добавить чизбургер, мне приходилось писать вот это:
```csharp
Catalog.Add(new MenuItem("Чизбургер", 99, "Бургеры", "url", true, true, false, false, false, false, false, false, false, true, false, false, true, true, true, true, false, false, false, false, false, false, true, true, true, false, false));
```
Читать это невозможно, понять, где какой ингредиент — нереально. 

После внедрения **паттерна Строитель** создание того же чизбургера превратилось в красивый и понятный текст:
```csharp
Catalog.Add(b.Create("Чизбургер", 99, "Бургеры").SetImage("url")
    .AddBuns().AddBeefPatty().AddCheese().AddPickle().AddOnion().AddKetchup().AddMustard()
    .AddExtraCheese().AddExtraBacon().AddExtraJalapeno().Build());
```

**Итоги внедрения:**
1.  **Читаемость кода выросла в разы.** Теперь создание меню читается как обычный рецепт.
2.  **Безопасность.** Риск перепутать порядок `bool` переменных полностью исчез.
3.  **Масштабируемость.** Если завтра маркетологи «Ростикса» решат добавить в меню креветки, мне нужно будет добавить всего один метод `AddShrimps()` в класс `MenuItemBuilder`. Старый код при этом никак не сломается и его не придется переписывать.
4.  Объекты создаются только в валидном состоянии: метод `Build()` возвращает готовый к использованию продукт.

Да, в начале пришлось потратить чуть больше времени на написание методов `Add...` в Строителе, но на масштабе хотя бы из 10-15 позиций меню это окупается моментально. Паттерн Строитель идеально подошел для решения проблемы объектов с большим количеством опциональных параметров. Код теперь выглядит профессионально и его не стыдно показать преподавателю.
