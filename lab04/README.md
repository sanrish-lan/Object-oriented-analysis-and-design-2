# Паттерн Загрузка по требованию

## 1. Описание проблемы

В системе мониторинга «CT-OS» (Томск-Хакер) обрабатывается база данных потенциальных целей. Каждая цель имеет:
1.  **Легкие данные**: ID и географические координаты (lat, lng) для отрисовки на карте.
2.  **Тяжелые данные (Intel)**: ФИО, ссылка на фото, номер банковского счета и баланс.

Если использовать загрузку сразу всех данных:
-   При старте системы серверу придется выкачать из БД тысячи записей с персональными данными, даже если хакер просто хочет посмотреть карту города.
-   **Расход памяти**: Хранение в RAM сотен фотографий и строк банковских данных, которые могут никогда не понадобиться.
-   **Низкая производительность**: Время запуска системы («ВРЕМЯ ЗАГРУЗКИ ДАННЫХ») вырастет в десятки раз из-за сложных SQL-запросов.

## 2. Решение: 

В проекте реализован паттерн **Загрузка по требованию** с использованием вспомогательного объекта-заместителя (**Proxy**). Тяжелые данные загружаются только тогда, когда пользователь выбирает конкретную цель на карте.

### Интерфейс Intel

Определяет контракт для получения секретных данных. Это позволяет системе работать как с реальными данными, так и с «заглушкой».

```java
interface Intel { 
    boolean loadDataFromDB(); 
    String getSecretData();   
}
```

### Proxy-объект (ProxyIntel)

Этот класс является «оберткой». При создании цели он не содержит никаких данных из БД, кроме ID.

```java
static class ProxyIntel implements Intel {
    private final int id;
    private RealIntel realIntel; 

    @Override
    public boolean loadDataFromDB() {
        if (realIntel == null) {
            realIntel = new RealIntel(id);
            return true;
        }
        return false;
    }
}
```

### Реальный объект (RealIntel)

Конструктор этого класса выполняет тяжелый SQL-запрос к таблице `secret_data`. Благодаря Lazy Load, этот код выполняется не при старте сервера, а «по требованию».



### API-слой для поэтапной загрузки

1.  `GET /api/targets` — возвращает список всех ID и координат. Работает мгновенно, так как данные уже в памяти.
2.  `GET /api/load?id=...` — активирует метод `loadDataFromDB()` для конкретной цели.
3.  `GET /api/hack?id=...` — возвращает уже загруженные данные.

## 3. Вывод

Применение Lazy Load в данном проекте позволило создать масштабируемую систему мониторинга:

**Плюсы:**
-   **Мгновенный старт**: В память загружаются только координаты (метод `loadMapNodes`), что позволяет системе быть готовой к работе за считанные миллисекунды.
-   **Экономия ресурсов**: Если в городе 10 000 целей, а хакер просмотрел только 5, то 9 995 тяжелых объектов не будут созданы, и 9 995 запросов к БД не будут выполнены.
-   **Гибкое управление состоянием**: Метод `reset()` в Proxy позволяет легко обнулять кэшированные данные (например, после кражи денег), заставляя систему перечитать актуальный баланс из БД при следующем обращении.

**Минусы:**
-   **Эффект «зависания» при первом клике**: Пользователь может заметить небольшую задержку при первом раскрытии данных цели, так как именно в этот момент идет обращение к файлу БД.
-   **Усложнение логики API**: Фронтенду необходимо делать два последовательных действия (загрузить и отобразить) вместо одного.

**Итог**: Для систем визуализации данных (карты, графы, списки), где количество объектов велико, а детальная информация нужна лишь для единиц, Lazy Load является единственным верным архитектурным решением.
